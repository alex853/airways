# Storage: страничный режим и отсечка хвоста

Статус: реализовано, включено в `Journeys` (`.paged()`, 2026-11-03), остальные хранилища на одном массиве. Код: `storage/Storage.java`,
`storage/ByteStore.java`, `FlatByteStore.java`, `PagedByteStore.java`; тесты `StoragePagedTest`.

## Зачем

Хранилище было одним `byte[]`. Рост такого массива копирует его целиком (для журналов около 20 МБ на 600 тысяч записей:
на копию нужно вдвое больше памяти, и массив должен лежать в хипе одним непрерывным куском). Журналы растут постоянно
(догонка c2c), и сервер упал с `OutOfMemoryError` в `Storage.addRecord` (2026-11-03). Загрузка (`readAllBytes`) и
сохранение (`copyOf` без резерва) тоже держат второй массив на весь размер.

## Как устроено

- Один `Storage`, внутри адаптер доступа к байтам `ByteStore` с двумя реализациями: `FlatByteStore` (один массив, режим
  по умолчанию, `growthStep` как раньше) и `PagedByteStore` (страницы). Вся логика полей, карантина и индекса heartbeat
  одна и работает через `get`/`set`/`getInt`/`setInt`/`fill`/`write`/`readString`/`ensureLength`/`load`/`save`.
- Включение в билдере: `.paged()` (страница 256 КБ, `Storage.DEFAULT_PAGE_SIZE_BYTES`) или `.paged(pageSizeBytes)`.
  `growthStep` вместе с `paged` не допускается (`build()` бросает `IllegalStateException`).
- Страница вмещает целое число записей, хвост страницы (меньше одной записи) не используется и не сохраняется.
  Запись и поле никогда не режутся между страницами. Новая запись, которая не поместилась, добавляет страницу, ничего
  не копируется. Страница выбирается по смещению: `offset / pageBytes`.
- Файл на диске **тот же самый** в обоих режимах: подряд записи, без резерва и без хвостов страниц. Файл одного режима
  грузится в другой (проверено тестом).
- Загрузка читает файл по страницам, сохранение пишет по страницам, массива на весь размер нет.

## Отсечка хвоста (`tryTrimTail`)

Когда журналы начнут умирать волной, последние страницы станут пустыми. `Storage.tryTrimTail()` смотрит последнюю
страницу: если на ней нет ни одной живой записи (удалены, в том числе на карантине, или ещё не созданы), страница
уничтожается, её записи убираются из очереди удалённых, дальше то же с предыдущей. Страница с хотя бы одной живой
записью останавливает отсечку.

- Карантин на отсечку не влияет: id отброшенных записей будут выданы новым записям заново (с конца, как новые id).
- Дыры в середине не трогаются и переиспользуются как раньше.
- Для хранилища на одном массиве «страница» равна одной записи: отсекаются мёртвые записи в конце по одной, массив
  остаётся.
- Результат `TrimResult`: записей и страниц до, сколько отброшено, сколько осталось, сколько записей на последней
  странице и сколько из них живых, сколько удалённых записей известно.
- `Journeys.tryTrimTail()` вызывается в `World.save()` перед сохранением и **каждый раз пишет строку в лог** (`j/y - paged storage tail trim: ...`), также когда ничего не отброшено.

## Статистика по статусам в логе

Раз в час (по реальному времени, первый раз при старте) `JourneyStats` пишет одну строку `j/y - stats by statuses: passengers total N: <статус>=<пассажиры>, ...; journeys total M: <статус>=<журни>, ...`: те же числа, что вверху страницы `tech/journeys` (`GET /admin/journey/stats`, это пассажиры, то есть размеры групп), плюс количество самих журни. Все статусы есть в строке, у пустых 0. Искать в логе по `j/y - stats by statuses`, часы сравнивать между собой.

## Что осталось

- Посмотреть лог отсечки (`j/y - paged storage tail trim`) на проде.
- Если пойдёт хорошо, перевести остальные хранилища (для мелких задать маленькую страницу через `paged(bytes)`) и
  не держать два режима.

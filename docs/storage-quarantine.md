# Storage: карантин удалённых записей

Статус: **реализовано** (см. раздел «Реализация» в конце). Задача: перестать мгновенно переиспользовать id только что
удалённых записей в in-memory стораджах (`net.simforge.airways2.storage.Storage`).

## Проблема

Записи в стораджах адресуются номером (`recordId`), ссылки между сущностями это просто числа
(`Journey.transportFlight1Id`, `TransportFlight.flightMissionId`, `Aircraft.locationAirportId` и т.д.). Если запись
удалена, а её номер сразу выдан новой записи, любая «висячая» ссылка на старую запись молча превращается в ссылку
на чужой объект. Проявления: журни «села» не на тот рейс, orphaned-журни, странные t/f и f/m в логах после
`FlightCleanup`.

## Как сейчас

- `Storage.addRecord` линейно сканирует от `recordId = 1` и берёт **первую удалённую запись** (то есть самый
  маленький свободный номер, почти всегда только что освобождённый). Скан O(n) на каждое создание.
- `Storage.deleteRecord` помечает заголовок (1 байт: 0 — существует, 1 — удалена), зануляет тело записи и вызывает
  `vacuumDeletedRecordsAtTail`, который отрезает удалённые записи с хвоста массива. Следующая дозапись получает
  **тот же** номер.
- Дозапись копирует весь массив (`new byte[data.length + recordSize]`), O(n) на каждую.

## Решение: карантин

Удалённая запись **не переиспользуется** в течение карантина N (на каждый сторадж свой). Время удаления хранится
в самой удалённой записи, поэтому переживает рестарты JVM.

### Хранение времени удаления

- Заголовок остаётся прежним (1 байт, 1 = удалена): `isDeleted` и формат файла не меняются.
- В первые 4 байта **тела** удалённой записи (`deleteRecord` сейчас пишет туда нули) записывается время удаления:
  `int`, минуты от `2020-01-01T00:00Z` по **реальному времени** (UTC). Это не «мировое» время, чтобы
  Storage не зависел от `World`. Переполнение через ~4 тыс. лет.
- Минимальное тело среди существующих стораджей 4 байта (`Airport2City`: `airportId` + `cityId`), то есть
  помещается везде. Добавить проверку в `Builder.build()`, чтобы новые стораджи не меньше 4 байт.
- Остальное тело зануляется как сейчас.
- Время `0` (старые файлы, до внедрения) читается как «возраст неизвестен».

### Алгоритм

`addRecord`:

1. Из очереди удалённых записей берём голову, если `now − deletedAt ≥ карантин`: переиспользуем её, **обнуляя
   всё тело** (включая 4 байта времени), ставим заголовок «существует».
2. Иначе дозаписываем в конец массива.

Очередь свободных записей (`ArrayDeque<int[]{recordId, deletedAt}>`, FIFO по времени удаления) строится при
`loadIfExists` (проход по записям, сортировка по `deletedAt`) и пополняется в `deleteRecord`. Время удаления
монотонно, поэтому голова всегда самая старая и достаточно проверять только её, а скан O(n) уходит.

Очередь **не сохраняется** (восстанавливается при загрузке из файла), состояние между рестартами не теряется.

### Vacuum

Отключить `vacuumDeletedRecordsAtTail` при удалении (мир сейчас растёт, а не сжимается). Если понадобится, то
отдельный метод `vacuum()`, который отрезает только хвост из записей старше карантина, и вызывается при загрузке
или из админки.

### Старые дырки при внедрении

В уже существующих файлах дырки с `deletedAt = 0`. Два варианта:
- **A (рекомендую):** при `loadIfExists` проставить им время загрузки. Всё удалённое «до» получает карантин N, ничего не
  переиспользуется в первые N суток после деплоя.
- **B:** считать их достаточно старыми и использовать сразу (как сейчас). Проще, но ссылки, удалённые прямо перед
  деплоем, ещё могут быть «живыми».

## Значения карантина (предложение, принято упрощённо: 1 сутки для всех)

Исходное предложение ниже оставлено как обоснование выбора; в реализации у всех стораджей один дефолт в 1 сутки.

Определяется самым долгоживущим «висячим» указателем на тип сущности:

| Сторадж | Карантин | Обоснование |
|---|---|---|
| Journeys | 7 суток | терминальные статусы чистятся через 1 сутки, `SpendingTheirTime` до 7 суток |
| TransportFlights, FlightMissions, ScheduledFlights | 7 суток | на них ссылаются журни (`LookingForTickets` с 1–3 суток паузы хранит старые `transportFlight1Id`) |
| Aircrafts | 7 суток | |
| EventLog, EventsToProcess, Airport2AirportDailyFlightStat | 1 сутки | на них никто не ссылается |
| Airports, Cities, Countries, Airport2City, AirportFacilities, CityFlows, City2CityFlows | 30 суток | теоретически удаляются, ссылок много |
| AircraftTypes, AircraftOperators | 30 суток | |

Размер роста массива = скорость удаления × карантин. Оценить заранее по `printDeletedRecordInfo`
(кол-во удалений в сутки по каждому сторадж-у).

Задаётся в `Storage.Builder`: `.deletedRecordQuarantine(Duration)`. В реализации по умолчанию **1 сутки** для всех
стораджей (`Storage.DEFAULT_DELETED_RECORD_QUARANTINE`), отдельных значений в сторадж-ах нет. Для записей меньше
4 байт данных дефолт не применяется (карантин отключается), явное значение > 0 для них даёт ошибку.

## Диагностика

- `printDeletedRecordInfo` дополнить: сколько удалённых в карантине / доступно к переиспользованию, возраст самой
  старой и самой свежей.
- Лог при переиспользовании записи (на уровне debug) и `warn`, если очередь упёрлась и мы растём из-за карантина
  заметно быстрее обычного.

## Риски и совместимость

- **Откат на старую версию.** Старый `addRecord` не обнуляет тело при переиспользовании (оно предполагалось
  нулевым). После отката первые 4 байта поля могли бы остаться ненулевыми в тех записях, которые были удалены
  новой версией. Смягчение: не откатываться на старую версию без прогона `scrub`, который заново зануляет тела
  всех удалённых записей (одна админская операция).
- **Рост хранилища.** После деплоя новые записи ~N суток растут дозаписью. Допустимо (мир растёт), но
  в `docs` и в мониторинге стоит учесть размер файлов стораджей.
- **Часы.** Используется реальное время, поэтому перевод часов сервера «назад» может удлинить карантин. Это
  безопасно (записи реже переиспользуются). Перевод «вперёд» сократит его, поэтому в алгоритме брать `max(0, now −
  deletedAt)`.
- **Вторая линия защиты.** Карантин не отменяет проверок консистентности ссылок (например, t/f хранит свой
  `flightMissionId`, и журни можно проверить на соответствие), они остаются.

## Что не входит

- **Generation в id** (например, 24 бита номер + 8 бит поколение): надёжнее, но меняет формат id и API
  (`Id.encode`), стоимость высокая. Рассматривать, если карантина окажется недостаточно.
- **Рост массива пачками** (capacity ≠ размер): отдельная оптимизация, не нужна для карантина, но желательна, если
  дозаписей станет больше.

## План реализации

1. `Storage`: поле `deletedAt` в теле удалённой записи, очередь, `Builder.deletedRecordQuarantine`, отключить
   vacuum при удалении.
2. Тесты на `Storage`: удаление и немедленное создание не возвращают тот же id, возврат после карантина, перезагрузка
   сохраняет время удаления, обнуление тела при переиспользовании.
3. Значения карантина для всех стораджей в `world/datamodel`.
4. Диагностика (`printDeletedRecordInfo`), запись в `docs/README.md`.

## Реализация

- `Storage`: время удаления (минуты от 2020-01-01 UTC, `int`) пишется в первые 4 байта тела удалённой записи;
  при создании записи тело зануляется. Очередь удалённых (`ArrayDeque`, самые старые впереди) строится при
  `loadIfExists`, не сохраняется. `addRecord` берёт голову очереди, если карантин закончился, иначе дозаписывает
  в конец. Vacuum хвоста при удалении убран, массив больше не сжимается.
- Старые файлы: у удалённых записей без времени (`0`) при загрузке ставится время загрузки (вариант A), то есть
  они получают полный карантин; порядок среди них по `recordId`.
- Разрешение времени: минута (время удаления усекается до минуты, запись освобождается не позже, чем через
  карантин). Часы реального времени (`System.currentTimeMillis`, для тестов `Builder.clock`). Если часы
  откатились, записи не освобождаются раньше времени.
- Сторадж с записью меньше 4 байт данных и карантином > 0 не создаётся (`IllegalStateException`).
- Значение: одно для всех, **1 сутки** (`Storage.DEFAULT_DELETED_RECORD_QUARANTINE`), отдельный класс констант
  убран. Если понадобится больше для journeys/t/f, достаточно `deletedRecordQuarantine(...)` в нужном сторадже.
- Диагностика: `getQuarantinedDeletedRecordCount()`, `getReusableDeletedRecordCount()`, дополнительная строка в
  `printDeletedRecordInfo`.
- Тесты: `StorageQuarantineTest` (42: границы карантина, порядок, сохранение/загрузка, старые файлы, мелкие записи,
  часы, случайные операции против модели), `DeletedRecordQuarantineWorldTest` (журни, самолёты, рейсы, события).
- Остаётся: утилита `scrub` для отката на старую версию (см. «Риски»), рост массива пачками.

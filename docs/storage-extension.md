# Расширение записи хранилища (инструкция)

Зачем: запись `Storage` лежит в файле «как есть», размер записи считается из полей. Файл старой раскладки, прочитанный новой, даёт мусор,
миграций в проекте нет. Поэтому любое изменение раскладки делается по шагам ниже.

## Сначала: нужно ли менять размер записи

Часто нет. Прошлые расширения (журни: цена, персоны: инициалы, рейсы: альтернаты) обошлись без смены размера: использовали резерв записи
или переопределили лишние байты. Тогда новые поля стоят **на тех же смещениях**, а «мусор» старых байтов обрабатывается разовой
разовой миграцией при загрузке (пример: аэропорты 2026-11-04, см. `airports-record-extension.md`; код миграции признаком опознавал старый файл и обнулял байты, потом был удалён). Если место в записи есть,
размер не меняем.

## Если размер записи надо менять: второе хранилище (проверено на персонах 2026-11-10)

Это четыре выкатки подряд, между ними несколько чистых рестартов и взгляд в лог. Пример целиком, с кодом и логами: [persons-record-extension.md](persons-record-extension.md) (`Persons.java` в коммитах
`e21a8cda`, `97621317`, `cc3ce9ff` и удаление старого). Хранилище здесь называется `X`, новое `X2` (имя файла другое, например `persons` и `persons2`); **после шага 4 имя `X2` остаётся**, переименование
потребовало бы миграции.

**Принципы:** старый файл главный, пока мы не убедились; всё, что копируется, копируется **обычными `getAsInt`/`set` по полям**, не байтами и не через внутренности `Storage`; расхождение это ошибка в
логе, а не падение и не автоматический ремонт; новые поля не используются, пока `X2` не стал основным.

### Шаг 1. Выкатка: `X2` рядом, пересоздаётся при каждой загрузке

1. В том же классе (`Persons`, `Airports`, ...) описывается `Storage` `X2` новой ширины: старые поля **на тех же местах и в том же порядке**, потом новые поля и резерв (размер записи кратен
   удобному, у персон 40). Такой же индекс heartbeat, если он есть. Объектом хранилища может быть просто `Integer` (`withInstantiator(id -> id)`): из `X2` сущности никто не читает.
2. Таблица соответствия полей основного хранилища полям `X2` (`IdentityHashMap<DataField, DataField>`): объекты `DataField` у разных хранилищ разные, поэтому поле одного для другого не годится.
3. **Загрузка** (`loadIfExists`): основное читается с диска как всегда, `X2` **не читается** с диска, а пересоздаётся из основного: `reset()`, потом для каждого id основного `addRecord()` (id
   должны совпасть, это проверяется) и копирование всех общих полей по полям; запись, удалённая в основном, удаляется и в `X2`. Так индекс heartbeat `X2` строится теми же `set`.
4. **Проверка «поле в поле»** (`...Mismatches`: последний id, живые и удалённые записи, значения общих полей, первые 20 расхождений): после копирования и **при каждом сохранении**. Расхождение пишется
   в лог ошибкой, мир не падает, успех пишется один раз при загрузке (`N records, no differences`).
5. **Все изменения основного повторяются в `X2`**: после каждого `storage.set` в сеттере сущности значение этого поля читается из основного и пишется в `X2` (`mirror(id, field)`). Осторожно с битовыми
   полями (`BitAccessField`): они пишут в хранилище мимо `set` сеттера, поэтому после битового сеттера копируется **всё поле**. `create` делает `addRecord()` в обоих (и сообщает ошибкой, если id разошлись),
   `deleteById` удаляет в обоих.
6. **Сохранение** (`save`): основное, проверка, `X2`. Мир сохраняет оба файла.
7. Тесты: `X2` равно основному после всех сеттеров (включая биты и удаление), размер файлов (`N * размер записи`), пересоздание при загрузке (в том числе удалённые записи и индекс heartbeat), расхождение
   сообщается списком, а не бросается.
8. Что смотреть в логе после выкатки и рестартов: одна строка `no differences` при загрузке, тишина при сохранениях, нет `OUT OF STEP`. **Новые поля пока не использовать**: `X2` пересоздаётся при
   каждой загрузке, их значения пропадут.

### Шаг 2. Выкатка: `X2` читается с диска, только проверяется

Пересоздание из основного убирается (копирующий код удаляется): `X2` читается с диска как сохранено (`X2.loadIfExists`), после загрузки только сверяется с основным тем же `...Mismatches`.
**Ничего не чинится**: расхождение или отсутствующий файл `X2` это ошибка в логе (`... DIFFERS ... AFTER THE LOAD (nothing is repaired)`), мир идёт дальше с основным. Остальное как на шаге 1: двойная запись и
проверка при сохранении. Тесты: загрузка с диска даёт совпадение; файл, изменённый вручную, и отсутствующий файл сообщаются и не чинятся. Если вылезло расхождение, кодом его не чинить, а откатиться на
шаг 1 и разобраться.

### Шаг 3. Выкатка: своп

Роли меняются: основным становится `X2` (из него читают и в него пишут сущности, у него индекс heartbeat, `Person::new` как конструктор объектов), а старое `X` остаётся **копией**: описание
хранилища 32-байтной раскладки, `mirror` из основного в `X`, проверка (`legacyStorageMismatches`) после загрузки и при каждом сохранении, оба файла сохраняются. Так код шага 2 ещё может прочитать мир,
**откат возможен**. Новые поля теперь переживают рестарт, но геттеров и сеттеров у них ещё нет. Лог: `the old storage is loaded from the disk and checked against the main one (X2) ... no differences`.
Тесты: копия равна основному, оба файла правильного размера, новые байты `X2` переживают сохранение и загрузку, расхождение и отсутствующий файл `X` сообщаются.

### Шаг 4. Выкатка: старое хранилище удаляется из кода

После нескольких чистых рестартов из класса убираются старое хранилище, таблица соответствия, `mirror`, проверка и тесты на копию. Код возвращается к тому, что был до расширения: отличаются только имя
файла (`X2`) и раскладка записи. Файл `X` **с диска удаляет владелец** после выкатки. С этого момента откат на старую раскладку только через бэкап мира. Потом вводятся геттеры и сеттеры новых полей.

### Подводные места, найденные на практике

- **id у основного и у `X2` должны идти синхронно.** Если сущности удаляются, основное по карантину может переиспользовать id, а `X2` выдать другой; у персон удалений нет, поэтому это просто ошибка в
  логе. Если удаления есть, нужен отдельный план (карантин и порядок переиспользования у обоих должны совпадать).
- Копировать байтами нельзя: `LatLong24bit` и подобные при перечитывании сдвигаются, а доступ к внутренностям `Storage` слишком инвазивен. Только `getAsInt`/`set` (и `getAsString`/`set` для строк).
- Тест на «изменённый вручную файл»: смещение поля в записи считается с учётом одного байта заголовка записи (первое поле на смещении 1).
- Перед каждой выкладкой есть бэкап мира, см. ниже.

## Мелочи

- Строки: `PlainString` стоит `length + 1` байт (байт длины). Для кодов фиксированной длины (ICAO, IATA) есть `FixedLengthString`: ровно
  `length` байт, строка кончается на первом нулевом байте или концом поля; пустая строка и `null` одно и то же, читаются как `null`.
- Если у поля меняется тип, но не позиция, миграция делается при загрузке и опознаёт старый файл по признаку, который новый файл дать не
  может (на аэропортах: во всех записях в новых байтах лежали длины строк); код миграции удаляется после первого деплоя и сохранения мира.
- Перед выкладкой есть бэкап мира (`DiskStorageStrategy` кладёт прежний мир в `world-data/<name>.backup/<millis>`); папки бэкапа должны
  называться числами.

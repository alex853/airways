# Person: пилоты и cabin crew (хранилище заведено пустым, логики нет)

Решено 2026-10-18. Раньше (ветка `master`, старый Airways на Postgres) были отдельные `Person` и `Pilot`, и это оказалось ошибкой:
пилот не имел своих полей, оба объекта надо было держать согласованными (`isSuitablePilot`, пары `person.status` / `pilot.status`).
Теперь **одна сущность** `Person`, и только для тех, кто имеет субъектность: пилоты и cabin crew. Пассажиры (груз журни) персонами
не становятся, журни остаются как есть.

Связанные доки: [users.md](users.md), [braindump-schedule-pay-pilots.md](braindump-schedule-pay-pilots.md),
[heartbeat-index.md](heartbeat-index.md).

## Принципы

- **User** это человек из реального мира: токен, способ входа, VATSIM CID. **Person** это то, как этот человек представлен внутри
  мира и как он с ним взаимодействует.
- User и Person знают друг друга: `User.personId` и `Person.userId`. Две ссылки заводятся и меняются в одном месте.
- PC или NPC определяется по `userId`: 0 это NPC, иначе PC. Отдельного поля нет.
- Фамилию и имя не храним (GDPR): только инициалы, максимум 2 буквы.
- Аватар выбирается из набора готовых картинок (смайлики, около сотни), загрузки своей нет.

## Состав Person

| Поле | Тип в Storage | Заметки |
|---|---|---|
| id | 24 бита | 65 тысяч могут не хватить (сотни тысяч при экипажах), 24 бита с запасом |
| heartbeat | по правилам хранилища мира | обязательно, см. сценарий ниже. Через `withHeartbeatIndex` ([heartbeat-index.md](heartbeat-index.md)) |
| type | 8 бит | `Pilot`, `CabinCrew`, список расширяем |
| userId | 16 бит | 0 = NPC |
| state | 8 бит | `Idle`, `OnDuty`, `Travelling`, `Resting` |
| locationType | 8 бит | 0 нигде / в пути, 1 City, 2 Airport, 3 Hotel, дальше по мере надобности |
| locationId | 16 бит | идёт по `locationType`. Города, аэропорты, самолёты уже 16 бит, отелей не больше 65 тысяч |
| originCityId | 16 бит | |
| initials | `PlainString`, длина 2 | как `AircraftOperators.iata` |
| avatarId | 16 бит | номер картинки из набора |

**`User`:** остаётся вне мира (property-файлы, пока без хранилища). Сейчас токен. Добавляются `personId` и VATSIM CID.
`lastLocationAirport` переезжает в локацию персоны (тип Airport). Деньги пока не проектируем.

**Не берём:** имя, фамилию, пол, базовый аэропорт, `journeyId`, назначения (`Assigned` не нужен: пилот на рейс через 10 часов просто
блокируется самим назначением, а не статусом), рабочее время, счётчики currency, расходы на гостиницу и питание. Это отдельные
шаги после того, как появится сама сущность.

## Что взято из старой системы

Старые `Person` и `Pilot` (master): `type`, `status`, `name`, `surname`, `sex`, `originCity`, `journey`, `locationCity`,
`locationAirport` и у пилота `type` (NPC/PC), `status` (`Idle`, `IdlePlanned`, `OnDuty`, `Travelling`), `person`.
Игрок привязывался заглушкой `SessionInfo` (personId, pilotId, vatsimPilotNumber).

| Старое | Как теперь |
|---|---|
| `Person.type` (`Ordinal`/`Excluded`) | не нужен, пассажиры не персоны |
| `Person.status` + `Pilot.status` (всегда ставились парой) | одно поле `state` |
| `IdlePlanned` (костыль аллокации) | убран, резервирование это назначение |
| `locationCity` + `locationAirport` (оба null это «в пути») | пара `locationType` + `locationId`, «в пути» это тип 0 |
| `Person.journey` | не нужен |
| `Pilot.type` NPC/PC | `userId` |
| `SessionInfo` (заглушка) | двусторонняя ссылка User ↔ Person |

Переходы старого пилота, которые надо учесть:
- `Idle → OnDuty` при старте рейса, `OnDuty → Idle` при финише.
- `Idle → Travelling` при поездке пилота (в старой системе это было журни из 1 человека), `Travelling → Idle` при прибытии.
- Локация: взлёт обнуляет аэропорт («в пути»), посадка (`blocksOn`) ставит аэропорт прилёта.

## Сценарий: пилот без присмотра пользователя (определяет heartbeat)

Пилот живёт сам по себе, пользователь им управляет, но если не управляет, у пилота есть **механизм автоматических действий**,
чтобы он не «замер».

Пример:
1. Пилот прилетел в Берлин, рейс закончен, пилот в аэропорту, `state` переходит `OnDuty → Idle`.
2. Пользователь закрыл всё и ушёл. Пилот остаётся в аэропорту.
3. При входе в `Idle` ставится **heartbeat примерно через 3 часа**.
4. Если за это время пользователь ничего не сделал, по heartbeat пилот **сам идёт в отель** (первый попавшийся; не самый выгодный) и,
   возможно, **поест** (не так дёшево, как хотелось бы пользователю).
5. Из отеля он уходит в состояние `Resting`, которое длится минимальное время.
6. Когда пользователь вернулся и хочет лететь, пилот может спать. Вывести его из `Resting` можно, но это либо невозможно до
   конца отдыха, либо ведёт к штрафу (меньше полётного времени, выше расходы). Какой вариант, не решено.

Значит пользователь управляет аватаром: кнопка «иди в гостиницу и спи» делает то же, что автомат, но когда и куда выбирает
игрок, и это выгоднее.

Что из этого следует для дизайна:
- `heartbeat` у Person нужен сразу, а процессор Person (по аналогии с `JourneyProcessor`) будет вызываться по нему.
- Состояний будет больше (`Resting`, возможно `Eating`): список не фиксируем.
- Появятся типы локации «отель», расходы, и надо будет решить, за чей счёт эти расходы (счёт пользователя или персоны).
- Автоматические действия лучше делать с рандомизацией времени и правилами «ближайший отель» (отелей в мире пока нет).

## Решения по открытым вопросам (2026-10-18)

- **Четыре состояния заводим сразу:** `Idle`, `OnDuty`, `Travelling`, `Resting`. Как они работают, пока не определено.
- **Ранний вылет из `Resting`:** точно уменьшенная выработка (недоспавший пилот), и зависит от значений: например, на очень длинный
  рейс недоспавшего пилота не поставить. Запрет или штраф решаем позже по этим значениям.
- **Автомат без отелей:** просто `Resting` на нестандартное число часов. Если пользователь после рейса сам нажал «Езжай в город» или
  «Отдыхай», пилот идёт как выбрал игрок. Если не нажал, пилот несколько часов мается в аэропорту, потом отдыхает сам, и вывести его
  оттуда сложнее и дороже. Как именно, пока не знаем.
- **Расходы и доходы:** деньги **персонажа**, а не пользователя. Зарабатывает персонаж. (Деньги пока не проектируем.)
- **`state` и `locationType`:** отель это локация, `Resting` это состояние, частично они дублируют друг друга. Пока оставляем оба,
  решим позже.
- **Cabin crew:** в ближайшее время не делаем, но тип в списке остаётся. Им понадобятся свой heartbeat и свой `Resting`, когда дойдём.
- **Токены:** в property-файл пользователя дописываются `personId` и VATSIM CID (для пользователя 1: `personId=1` и CID автора).
  Читалка (`UserStorage`) учит читать эти значения.

## Размер записи

Формат записи по соглашению хранилищ мира: заголовок 1 байт (признак удалённой записи), id не хранится (это номер записи).

| Поле | Байт |
|---|---|
| заголовок записи | 1 |
| type | 1 |
| userId | 2 |
| state | 1 |
| heartbeat (`Signed32bit`, нужен для `HeartbeatIndex`) | 4 |
| locationType | 1 |
| locationId | 2 |
| originCityId | 2 |
| initials (`PlainString` длины 2 = длина 1 байт + 2 символа) | 3 |
| avatarId | 2 |
| **итого** | **19** |

Как у журни, округляем запись до 32 байт: **13 байт резерва** (под рабочее время, счётчики currency, last night takeoff/landing).
Для 200 тысяч персон это около 6,4 МБ.

## Рабочее время, currency и «последний ночной» (решено: отдельно от Person)

Запись `Person` фиксируем на **32 байтах** (19 занято, 13 резерв). Рабочее время, счётчики currency и last night takeoff/landing в
`Person` **не кладём**: счётчики не помещаются (на пары «дата-время + наработка» в 13 байт влезает около 3 штук), а 64 байта на
запись слишком много.

**Идея: это всё производные от одного журнала полётов (логбук), а не отдельные поля.** Каждая посадка или рейс персоны это
запись логбука, а рабочее время, посадки за 90 дней на типе, последний ночной взлёт или посадка считаются выборкой по нему.
Отдельного хранилища «счётчиков» не нужно, хранится только факт.

Черновик записи логбука (не решено, оценка размера):

| Поле | Байт | Заметка |
|---|---|---|
| personId | 3 | |
| время взлёта в минутах от 2025-01-01 | 3 | 24 бита по минутам это около 31 года |
| наработка (0.1 часа) | 1 | до 25 часов |
| aircraftTypeId | 1–2 | |
| флаги (ночной взлёт, ночная посадка, посадка состоялась) | 1 | |
| аэропорт вылета, аэропорт прилёта | 2 + 2 | |
| id миссии | 3 | |
| заголовок | 1 | |
| **итого** | **около 18** | |

Если всё же понадобится быстрый доступ к «дате последнего ночного взлёта и посадки» без выборки, это две даты. Размер даты в днях
от 2025-01-01: 10 лет это 3652 дня, то есть 12 бит (до 4095 дней, примерно 11 лет), практически берём `Unsigned16bit` (179 лет).
Две даты это 4 байта, они влезают в резерв `Person`, но пока их не заводим.

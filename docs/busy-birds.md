# BusyBirds

Оператор бизнес-авиации (`World25.BusyBirdsOperatorId`). Игрок (пилот-человек, `CharacterMode.PC`) берёт
«миссии» — это журнеи (`Journeys.Journey`) пассажиров, которые хотят премиальный сервис — и сам их выполняет
на парке самолётов BusyBirds.

## Компоненты

| Компонент | Файл | Роль |
|---|---|---|
| `BusyBirdsController` | `app/user/BusyBirdsController.java` | REST API `/busy-birds`, DTO, оркестрация бронирования |
| `BusyBirdsMissionControl` | `world/processors/BusyBirdsMissionControl.java` | Бизнес-логика: список миссий, оплата, построение планов |

`world.busyBirdsMissionControl()` — доступ к логике из `World`.

## REST API (`/busy-birds`, `@CrossOrigin`, `userId` из request attribute)

Чтение идёт через `worldBean.read(...)`, запись — через `worldBean.modifySync(...)`.
Во всех методах первым вызывается `checkUserHasAccessToBusyBirds(userId)` (сейчас пустая заглушка).

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/cities` | Все города по имени (для дропдаунов страницы) |
| GET | `/mission/to-book?fromCityId=&toCityId=` | Миссии между выбранными городами (нужен хотя бы один, без обоих пустой список: журни слишком много); сортировка по городу вылета, затем прилёта |
| GET | `/aircraft/available` | Самолёты BusyBirds, на которых пользователь может букать: свободные (idle в аэропорту, нет ни одной незавершённой миссии) и те, у которых все незавершённые миссии его собственные (продолжение). В ответе `locationAirportIcao` это аэропорт, где самолёт окажется к началу новой миссии, `earliestStart` (UTC мс) это 0 для свободного самолёта и посадка последней его миссии плюс 30 минут для остальных |
| GET | `/mission/build-plans?missionId&aircraftId&startTime[&pauses][&ferryBackToBase=true]` | Варианты планов выполнения миссии для старта `startTime` (UTC миллисекунды, обязателен); каждый план несёт `startTime`, `endTime` и `slot` (свободно ли время в ростере) |
| PUT | `/mission/book?missionId&aircraftId&startTime&planId[&pauses][&ferryBackToBase]` | Бронирование выбранного плана в ростер |

Режим один (с 2026-11-06): букинг миссий делается на странице `busy-birds.html`; из вкладки Airways в G7 букинг убран, вместе с ним удалены `PUT /ferry/book` (свободный ферри-рейс без миссии),
`GET /booking-status` и все параметры, которые держались ради G7 (`ignorePilotState`, `turnaroundTime`, `intervals`, путь без `startTime`).

ID наружу кодируются `Id.encode/decode`. `missionId` == id журнея.

## Бизнес-логика

### Что считается миссией
Журней в статусе `LookingForTickets` с `preferredCabinService` = `F` или `J`.
Отдельной сущности миссии пока нет — `Mission` это вычисляемая обёртка над журнеем
(`journey`, `validTill` (пока всегда null), `distance`, `pay`).

### Расстояние и оплата
- `distance` = расстояние по прямой между координатами городов (nm, int).
- `pay = ((distance / 400) * 7000 + 2000) * (1 + d(fromCity)*0.01) * (1 + d(toCity)*0.01) * (1 + d(journey)*0.01)`,
  где `d(x)` = последняя цифра id (`Tools.lastDigit`). Т.е. база 2000 + 7000 за каждые 400 nm,
  плюс детерминированный «шум» до +9% по каждому из трёх множителей (стабилен между запросами, не random).

### Оплата пилота (реализовано как показ в планах, начисления нет)

Решено 2026-10-18: занимаемся только BusyBirds, универсальную модель оплаты для других операторов не делаем. Деньги целые, без дробей.
Пилоту за плечо платят из двух частей (`BusyBirdsPilotPay`, ответ `/mission/build-plans`, поле `salary`):

| Часть | Формула | Для каких плеч |
|---|---|---|
| `flightPay` (за налёт) | базовая часовая ставка типа × время плеча от blocks off до blocks on в часах: при Book плановое (лётное время плюс 20 минут руления, это оценка), при выплате фактическое (с 2026-11-02), округление до целого | все плечи (revenue и reposition) |
| `incomeShare` (доля дохода) | 3% × доход миссии (`pay` журни), округление до целого (половина вверх) | только revenue-плечо |
| `total` | `flightPay + incomeShare` | |

Базовые часовые ставки (парк BusyBirds, 7 бортов, ориентиры из реальных ставок бизнес-пилотов США: Citation CJ2 примерно $95–150k в год,
Gulfstream G600/G700 примерно $300–370k):

| Тип (ICAO) | Самолёт | Бортов | Салон | Базовая ставка в час |
|---|---|---|---|---|
| C25C | Citation CJ2 | 3 (BB-CJA, BB-CJB, BB-CJC) | J8 | 200 |
| GLF6 | Gulfstream G600 | 2 (BB-GLC, BB-GLD) | J14 | 500 |
| GA7C | Gulfstream G700 | 2 (BB-GLA, BB-GLB) | J16 | 500 |
| другой тип | | | | 200 (по умолчанию, warning в лог) |

Пример (Лондон-Фарнборо → Париж → Берлин → Лондон на C25C): первое плечо `flightPay` только (~1 ч × 200), второе плечо (Париж →
Берлин, revenue, ~2 ч) 2 × 200 + 3% дохода, третье `flightPay` только. План выдаёт `salary` по каждому плечу и общий `salary` по
плану (сумма плеч).

**Коэффициенты (не реализовано, `todo ak3` в `BusyBirdsPilotPay`).** Выплата зависит от currency пилота (решено 2026-10-19, см. [persons-pilots.md](persons-pilots.md), раздел «Рейтинги, currency и их продление»). Обе части будут домножаться на коэффициенты:
тайп-рейтинг, посадки за последние 90 дней, ночные посадки, опыт (журнал полётов, см.
[braindump-schedule-pay-pilots.md](braindump-schedule-pay-pilots.md)). Пока коэффициенты равны 1. Эффективность ферри-плеч для
оплаты определим позже. Зарабатывает **персонаж** (деньги персонажа, а не пользователя), счетов и транзакций пока нет.

**Когда платят.** В момент завершения рейса: `FlightMissionControl.finish` вызывает `BusyBirdsMissionControl.payPilot`. Платёж происходит только для рейса самолёта BusyBirds и только если у рейса есть пилот (персона пользователя), отменённые рейсы не оплачиваются. Платят за **плановую** длительность рейса (по миссии, фактическое время не влияет). Если у рейса есть transport flight, он считается revenue-плечом, и к `flightPay` добавляется 3% дохода журни этого t/f (доход считается по городам поездки). Счетов и транзакций пока нет, платёж только пишется в лог:
`p/s #1, f/m #5, t/f #7 - BusyBirds flight, pilot gets paid 3500 (flight pay 400, income share 3100)` (для рейса без пассажиров `t/f none`).

Веб-морда (`busy-birds.html`): в таблице плеч две новые колонки `Flight pay` и `Income share` и итоговая строка по плану.

**Котировка считает оплату с учётом квалификаций (2026-10-21).** `buildPlans` получает параметры оплаты пилота на этом типе (`PilotPayParams`, их берёт `BusyBirdsController.payParamsOfUser`: currency и уровень опыта),
и оплата каждого плеча это то, что пилот реально получит: полётные `PilotPay.flightPay(базовые полётные, параметры)`, доля `PilotPay.incomeShare(доход, параметры)` (доля по уровню опыта, вычеты за currency), у перегонного плеча доли нет.
Те же параметры получает контракт при Book, поэтому цифры в котировке и в контракте совпадают (кроме ручного режима, он ставится на старте рейса). Плечо несёт состав оплаты (`SalaryDto.forLeg`:
часы с двумя знаками, ставка пилота, доход миссии, процент доли), страница объясняет числа во всплывающих подсказках значков F и I («375 × 0.87 h», «0.375% of 10 445»), в самой таблице только числа. В шапке окна котировки справа от самолёта показаны «Your hourly pay» и
«Income share», справа от маршрута «Mission income». Прежняя фиксированная доля 3% убрана.

**Условия пилота на самолёте (2026-10-21).** Когда на странице выбран самолёт, под ним показывается блок «Your terms on this aircraft» (`GET /busy-birds/pilot-terms?aircraftId=`, считает сервер, `BusyBirdsController.buildPilotTerms`): слева (~20%) квалификации пилота на этом типе (уровень опыта, type currency, night flying, can carry passengers), справа две части: **Pay for flown hours** (базовая ставка типа, вычеты в процентах, итог «ставка × коэффициент = за час полёта») и **Income share** (базовый процент по уровню, вычеты, итог «процент × коэффициент = процент от дохода миссии»). Смена самолёта пересчитывает блок, раз в минуту он перезапрашивается, поэтому изменение квалификаций видно. Режим manual в блоке пока не показывается. Вычеты и коэффициенты те же, что в `PilotPay` (см. flight-contracts.md).

### Выбор аэропортов города (`listAirports`)
Для города берутся неисключённые (`!isExcluded`) аэропорты. Приоритет:
1. Базовый аэропорт BusyBirds (`BaseAirport` для оператора) — возвращается один он;
2. Бизнес-терминалы (`BusinessAviationTerminal`) этого оператора;
3. Любые бизнес-терминалы;
4. Все аэропорты города.

### Самолёт во времени: продолжение миссии (с 2026-11-06)
Самолёт BusyBirds это ресурс во времени. `BusyBirdsMissionControl.outlooks(самолёты)` (один проход по хранилищу рейсов, `FlightMissions.byAircraftIdIn` плюс незавершённые статусы) для каждого самолёта даёт
`AircraftOutlook`: где он будет и с какого момента свободен. Без незавершённых миссий это его нынешний аэропорт и «свободен сразу». С миссиями: аэропорт назначения **последней** по плановой посадке
миссии и её посадка (`freeFromWorldTime`); незавершённые это все статусы кроме `Finished` и `Cancelled`.
- Самолёт доступен пользователю, если миссий нет (и он idle в аэропорту) или все его незавершённые миссии принадлежат этому пользователю (`isOpenTo`). Самолёт с миссиями другого пилота (или нескольких, или без пользователя) не предлагается, `build-plans` и `book` отвечают «The aircraft has missions of another pilot.»
- План строится от аэропорта из `outlook` (подлёт к журни считается оттуда, а не от нынешнего места самолёта), `buildPlans(journey, aircraft, aircraftAirport, ...)`.
- Слот плана получает `aircraftBusy` и `aircraftEarliestStart`: начало новой миссии раньше посадки последней миссии самолёта плюс 30 минут отклоняется (`StartSlotDto.free` ложно, `book` отказывает словами «The aircraft is busy…»).
  Это закрывает и старое ограничение «два букинга на один самолёт на одно время». Вставить миссию между двумя уже забукованными нельзя: новая идёт только после последней.
- Страница: самолёт с миссиями подписан «· from <время>», с адресом `busy-birds.html?aircraft=<id>` он выбирается сам (так открывает серая плитка «Book the next flight» в ростере у цепочки
  BusyBirds, она есть только у последней цепочки самолёта), «City from» ставится по аэродрому, где самолёт окажется, «As soon as possible» означает «когда самолёт освободится», время старта нельзя выбрать раньше.

### Построение планов (`buildPlans`)
Для каждой пары (аэропорт вылета × аэропорт прилёта) строится свой план; планы сортируются по
суммарной дистанции (кратчайший первым). Параметры: `startTime`, `pauses`, `ferryBackToBase`.

Структура плана (`_buildPlan`):
1. **Reposition** из текущего аэропорта самолёта в аэропорт вылета — если самолёт стоит не там.
2. **Revenue** — рейс с пассажирами (`pax = journey.groupSize`).
3. **Reposition** в ближайший базовый аэропорт BusyBirds (ближайший к аэропорту прилёта) — если
   прилёт не в базе И `ferryBackToBase = true`.

Время: `startTime` (UTC миллисекунды, обязателен) задаёт вылет первого плеча, он выравнивается вверх до 5 минут, как вылет каждого плеча. Паузы перед вторым, третьим плечом: параметр `pauses`
(часы через запятую, `0.5,3`; значение вне 0..48 часов отклоняется, 400), по умолчанию 30 минут, это минимум зазора ростера. Страница паузы не спрашивает, всем ставится 30 минут (решено 2026-11-06),
выбор остался на сервере.
**Времена ног это времена их миссий:** от blocks off до blocks on (лётное время плюс 10 минут руления до взлёта и 10 после посадки), посадка ноги в плане это blocks on, поэтому пауза в 30 минут между
ногами это настоящий зазор ростера между рейсами (его минимум 30 минут), а конец блока для слота это blocks on последней ноги. (До 2026-11-06 план считал посадку без руления, и зазор в ростере был на 20 минут
меньше паузы; сквозной тест букинга `BusyBirdsBookingStartTimeTest` это поймал.)
**Слот в ростере:** каждый план несёт `startTime` и `endTime` (первый вылет и последняя посадка, UTC миллисекунды) и `slot` (`BusyBirdsController.checkStartSlot`): весь блок плеч с паузами это один интервал,
он должен начинаться не раньше чем через 30 минут от сейчас (допуск 5 минут на разницу часов браузера и сервера, `tooSoon`), не позже чем через 7 дней (`tooLate`) и держать не меньше 30 минут до каждого
рейса пилота, который не закончен и не отменён (то же правило, что у ShadowJet, `ShadowJetBooking.checkSlot`; чужие рейсы и состояние пилота не смотрятся); `conflict` это первый мешающий рейс.
Время вылета выравнивается на 5 минут (`Time.alignTo5mins`), длительность — `SimpleFlight` по
`AircraftPerformanceData` типа ВС. ID плана = `"<ICAO from>-<ICAO to>"`.

### Бронирование (`PUT /mission/book`)
План **пересчитывается заново** и ищется по `planId` (серверного хранения планов нет — план stateless).
Нужен только пилот пользователя (`BusyBirdsController.noPilotProblem`): состояние и место пилота не проверяются, как у ShadowJet (решено 2026-10-30, сделано для BusyBirds 2026-11-06): пилот сам приходит к
самолёту и начинает рейс. Весь блок плеч проверяется по слоту ростера; при `!slot.free` ответ `failure` со словами, ничего не создаётся.
Ошибки возвращаются как `BookMissionResponse("failure", messages)` (не исключением): план не найден
или план в статусе Failure.

Для каждого плеча:
1. `FlightMissionHelper.scheduleDispatchedMission(...)` — создаётся диспетчированная лётная миссия
   и событие `PilotOnDuty`; на миссии ставится `CharacterMode.PC` и `userId`.
2. Если плечо `Revenue`: создаётся `TransportFlight`, на него выкупаются билеты на всю группу
   в классе `J`, у журнея выставляются `transportFlight1Id` и `bookedCabinService = J`,
   журней переводится в `waitForCheckin`.

Допущение: все самолёты BusyBirds имеют только J-компоновку салона.

## Известные ограничения / TODO (из кода)

- `checkUserHasAccessToBusyBirds` — заглушка, доступ не проверяется.
- `buildPlans` собирает `messages` о проблемах (самолёт не idle/не припаркован, нет аэропортов), но
  `_buildPlan` их не использует: ни одного плана со статусом `Failure` сейчас не создаётся.
  Следствие: бронирование проверяет только `planId`, **состояние самолёта на бронировании не валидируется**
  (на практике защищает только то, что список `/aircraft/available` показывает idle-самолёты).
  Если аэропортов нет, циклы пусты и вернётся пустой список планов.
- Не учитывается максимальная дальность ВС и вместимость кресел vs размер группы
  (`todo ak2` в начале `BusyBirdsMissionControl.buildPlans`, перенесены туда 2026-10-23 при удалении неиспользуемого кода).
- `Mission.validTill` всегда null — срока жизни миссии нет.
- `pay` (доход миссии) и `salary` (оплата пилота) показываются в планах, при завершении рейса платёж только пишется в лог (`payPilot`), счетов и транзакций нет.
- Несколько журнеев/миссий можно забронировать на один самолёт подряд без проверки пересечений
  (после первой брони статус самолёта зависит от обработки лётной миссии).
- `Geo.distance` — прямая; `totalDistance` плана включает reposition-плечи.
- Хранилище персистентных миссий **не сделано**: миссии вычисляются на лету. Заготовка класса `BusyBirdsMissions` (скопированная из фасилити,
  нигде не использовалась) удалена 2026-10-23, она осталась в истории git. Задуманная схема: status, journeyId, pilotId, aircraftId, createdAt, assignedAt,
  до трёх пар flightMission+transportFlight. Это направление развития: хранить миссии вместо вычисления на лету.
- В `bookMission` вся цепочка внутри `modifySync` не атомарна относительно ошибок посередине
  (исключение на 2-м плече оставит созданным 1-е).
